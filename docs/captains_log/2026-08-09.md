## Removing `avian`

Removing Avian from the physics simulation ended up refactoring out some of the
`uom` unit conversion types. The density components/types were integrated with
the collider, so we need to roll our own basic mass properties and density
types. We pretty much do this already with the ideal gas law implementation so
in the end we are left with a more unified system under the hood.

Similarly, Avian maintains a special "Physics Time" resource that tracks the
physics timesteps independently from the "game time" resource. This allows for
fast-forwarding or slow-motion playback and decouples the physics update loop
from the game tick or render frame rate.

## Merging buoy-runtime with buoy-physics

Both of these crates are "the engine" of the simulation. Originally, the split
was planned as a way keep the bevy application code separate from the physics
simulation code. This made the dependencies nice and neat but made the app
development workflow more complex, especially when working on both crates
simultaneously or exposing data from the physics simulation to the bevy app for
things like debugging text and physics telemetry.

These benefits to having a separate physics and headless runtime crate are not
actually that significant. For headless mode, the CLI can be a standalone crate
(in the same way as `bevy-ui`) or confined to an executable in
`buoy-physics/bin/` allowing for the same separation of concerns in GUI mode and
headless mode.

Maybe it makes sense to rename `buoy-physics` to `buoy-core` now? I'll hold that
decision until a clearer reason comes up.

Looking at an old [pull request](https://github.com/philiplinden/buoy/pull/42)
one reason to split the physics from the runtime is so that the physics can be
used _without a bevy dependency_ (not to switch physics backends).

## Should the physics depend on bevy?

Decision: **keep it one crate.** Draw the seam with modules and a CI check
instead of a crate boundary.

Looking at how deep bevy actually goes, it's thinner than the
`use bevy::prelude::*` at the top of every file makes it look. The equations
(`ideal_gas_volume`, `ideal_gas_density`, `coesa_temperature`, `coesa_pressure`,
`drag`, `buoyancy`, `local_gravity`) are already plain functions over `uom`
quantities and `Vec3`, and `Vec3` is `glam`, which bevy only re-exports. What's
actually bevy-specific is `#[derive(Component)]`/`#[derive(Resource)]` on
otherwise-plain structs plus the systems that schedule them (`integrate` in
`forces.rs`, the `plugin()` fns). That's the runtime stepping the sim, not the
physics itself.

 The orphan rule blocks implementing a foreign trait for a
foreign type (you can't `#[derive(Component)]` on a type from
another crate), so a `buoy-core` split would force newtype wrappers around
`GasSpecies`, `IdealGas`, `Atmosphere`, and the `Asset`/`TypePath`/`Reflect`
config types. That's `.0` or a `Deref` impl at every use site, forever.

The reason I merged the crates back together was surfacing physics data to the
app for debug text and telemetry. The ecosystem's answer to that under a split is
[`bevy_mod_component_mirror`](https://github.com/devildahu/bevy_mod_component_mirror),
an entire crate that exists because Rapier's foreign components don't implement
`Reflect` so you can't tune them in the inspector without a restart.

Avian's founding principle was explicitly "no wrappers around existing engines"
on the grounds that a wrapper has to maintain a separate physics world and sync
it back every frame. [`bevy_rapier`](https://github.com/dimforge/bevy_rapier/pull/138)
implements a wrapper type per rapier type, a dedicated writeback stage, a full
rewrite just for ergonomics, and one ergonomics win that had to be reverted for
being too slow.

The wrapper-tax comparison isn't perfectly fair to my use case. Rapier
owns its own simulation state, so it needs the dual world and the sync. A
`buoy-core` of plain structs and pure functions wouldn't own any state, the
wrapper components would hold the only copy. My version of the split really
would be cheaper than theirs.

Bevy itself is moving *away* from feature
flags and toward separate crates ([splitting `bevy_core`](https://github.com/bevyengine/bevy/issues/16892),
`bevy_utils`). But that's a 40-crate engine solving modularity so consumers can
drop the renderer. The Bevy 
[plugin dev guide](https://bevy.org/learn/quick-start/plugin-development/) says
to put optional deps behind cargo features, though.

I wanted the split because it feels cleaner, but there is no real need for it.
Nothing concrete needs a bevy-free core right now: headless already works
without render features, and the math is already pure enough to unit test as-is.

A module seam (isolating bevy behind an `ecs.rs` module, for example) satisfies
this basically for free:

- `core`-ish modules: plain types, pure functions, no bevy imports
- ECS modules: the derives, the systems, the `plugin()` fns
- CI builds `--no-default-features` so a stray `use bevy::prelude::*` fails loud

## Simulating ambient fluid

I had an idea for the ambient compressible fluid simulation using signed
distance functions to evaluate drag and pressures as the object moves through
the fluid. 

Most (all?) fluid simulations discretize the environment into a grid of cells,
then solve the fluid equations on this grid with energy conservation across
cell boundaries.

- If we use a cell-based approach for physics (a la `big_space`), then this is
  a natural extension for simulating ambient conditions.
- If we use a shader for pressure-based physics derivations, then the primary
  object ends up calculating its own pressure field from the fluid simulation
  "inside out" (i.e. from the object's own geometry and fluid interactions).

A shader-based approach makes the environment's field continuous. This might
not be better than discretizing the environment into cells, though, since
far-field interactions are not relevant during the simulation. Additionally,
real pressure data from the national weather service or NOAA is provided as a
grid of values anyway. Interpolation is needed to evaluate the field at
arbitrary points but we can guarantee conditions at cell boundaries are
conserved and match the real empirical data. A shader, on the other hand, could
be loaded from a texture and have arbitrary resolution _separate_ from the
spatial resolution of the rigid body dynamics. Procedural texture generation is
not all that complicated (using noise and spectral density functions) and can be
done efficiently on the GPU.

A non-rust example of fluid sim shader is [bassicali/inkbox](https://github.com/bassicali/inkbox)
![screenshot-of-inkbox](https://github.com/bassicali/inkbox/raw/main/images/screen1.png)
and a Bevy example shader is [narasan49/bevy_eulerian_fluid](https://github.com/narasan49/bevy_eulerian_fluid).
