# 2025-08-16

I spent a while working on
[bevy_repl](https://github.com/philiplinden/bevy_repl) in order to provide some
at-runtime control over the simulation without implementing a full-blown UI. I
think it works pretty well. It also gave me a lot of clarity on how to structure
bevy apps.

Now that I can interact with the simulation without graphics or windowing, it is
safe to ignore the `buoy-ui` crate and focus on the physics.

Speaking of which, how about another rewrite? ;)

I have been thinking about this multi-crate approach for a while, and I finally
have a coherent opinion. I think it is a great idea to split the rendering,
graphics, and UI from the core simulation crate. This allows the simulation to
be used as an _engine_ for physics simulations, without any bloated dependencies
on graphics or UI. It also allows for greater flexibility in how the simulation
is used, as it can be used in a variety of contexts, such as in a game, a
scientific simulation, or a research tool.

As for other crates, I think it was a mistake to separate the pure-rust physics
implementation from the Bevy app. It is best to lean into Bevy's ECS and plugin
system when structuring the simulation itself, because the simulation is, after
all, a careful sequence of discrete events (frames) that are processed
sequentially and in a deterministic manner. That's a Bevy app.

So what does belong in a separate crate? I think the best candidates for this
are things like objects or materials, fluids (like atmosphere or water), or
environments (like open water or windy air, more broadly than just the fluid).
Each of these is a collection of systems that are self-contained and relatively
isolated, and are things that I can imagine swapping out for different
implementations. For example, for underwater environments we don't need to load
the atmosphere or balloon crates, and for balloon simulations we don't need to
load the underwater crate.

That's all in the future, though. For now instead of separate _crates_ it is
sufficient to separate these into different _modules_ and/or Bevy plugins. Later
on, refactoring plugins into separate crates will be a matter of moving files
and changing pretty much only the `use` statements elsewhere.

For now, I'll make placeholder crates to demonstrate the architecture with the
UI features. I won't be developing those for a while, so it's just for
demonstration and shouldn't break things too badly.
